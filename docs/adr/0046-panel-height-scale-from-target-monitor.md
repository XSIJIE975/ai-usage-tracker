# ADR-0046: 面板高度换算取目标显示器 scale，唤出前工作区硬上限

状态：已接受　日期：2026-11-11　关联：ADR-0016、ADR-0027、ADR-0045

## 背景

ADR-0045 修复了「显示设置变化后唤出面板被裁切/移出屏幕」，但其后果一节「唤出后读到的窗口 scale 已是修复后的新值」的假设被 release 版实测证伪：速览面板（托盘左键唤出）在缩放比例变化后唤出，高度占满整个工作区、底部盖住系统任务栏，重启即恢复。

病根在前端高度自适应（`useFitWindowHeight`，ADR-0016 引入）的物理换算：

- 高度上限用 `currentMonitor()` 的**实时**显示器 scale 把工作区换算成逻辑值（80% 上限本身正确）；
- 补间落笔却用 `panel.scaleFactor()`——**窗口缓存 scale**——把逻辑高度乘回物理像素。

隐藏窗口收不到 `WM_DPICHANGED`（ADR-0045 的同源事实），而 `ensure_on_screen` 在唤出路径里只修尺寸/位置、且同屏改缩放不产生窗口移动时 WebView/tao 的缓存 scale 在 show 后也未必刷新。缓存 scale 偏高（如 125% → 100%）时：物理高度 = 0.8 × 工作区 × 1.25 = **恰为整个工作区**，位置又被钳回工作区上缘——面板从工作区顶铺到任务栏，正是实测现象；缓存偏低时反向表现为面板偏矮。

「尺寸换算必须用目标显示器 scale，不能信窗口缓存值」这条教训已在 Rust 侧落过两次（ADR-0027 锚定、ADR-0045 唤出修复），这次是它在同一条唤出链路前端半边的漏网之鱼。

## 决策

**1. 高度换算的 scale 一律取目标显示器（`currentMonitor()`）的实时 scaleFactor；窗口缓存 `panel.scaleFactor()` 仅作显示器查询失败时的兜底。** 贴边锚定的补间随之统一用显示器实时值，`clampPanelHeight` 提为纯函数锁定公式。

**2. 上限口径不变：`clamp(minHeight, floor(工作区物理高 ÷ 显示器 scale × 80%), 内容自然高)`。** 基准是工作区（不含任务栏/菜单栏），天然不遮系统栏；比例不做设置项。

**3. Rust `ensure_on_screen` 唤出前对面板物理高度加硬上限（≤ 目标显示器工作区高度）。** 防御纵深：前端任何回归把窗口写超工作区，该尺寸最多存续到下次唤出即被修复；高度是自适应维度（前端按内容随时重算）钳矮安全，宽度是固定布局不钳。

**4. 溢出可见性：滚动条保持全局隐藏风格，内容可继续下滚时在滚动容器底缘叠渐隐遮罩**（`ScrollFadeHint`，滚到底即消失）——内容超上限进内部滚动是常态路径，需要有「下方还有内容」的提示。

## 后果

- 三条唤出路径（热键/托盘菜单/托盘左键锚定）共用同一钩子，一次修复全收；正常路径少一次 `scale_factor()` IPC。
- 显示器查询失败的兜底路径没有工作区上限，越界窗口由决策 3 在**下次唤出**修复（当次仍可能越界，查询失败本身已属异常态）。
- 跨平台共用同一几何逻辑，无平台分支：workArea/scale 由 tao 按平台提供（Windows 工作区不含任务栏、macOS visibleFrame 不含菜单栏/Dock）；Linux X11 工作区不可靠时上限退化为整屏 80%，仍不溢出（ADR-0016 的教训已含此容忍）。
- 前端测试锁定换算公式与兜底语义；Rust 测试锁定硬上限纯函数。

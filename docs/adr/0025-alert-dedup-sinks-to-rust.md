# 告警去重下沉 Rust：协调器状态持久化与后端冷却守卫

Status: accepted

## Context

2026-09-11 用户报告：启动时告警过一次后，按 F5 重载前端（dev 与 release 均可）会在同一状况下再次触发告警。代码核对：

- 告警去重靠两份状态——边沿态 `triggered` 与冷却时间戳 `lastNotifiedAt`——存在 `AlertCoordinator` 的 JS 内存 `Map`（`src/alerts/coordinator.ts`），而协调器是主窗口 webview 的模块级单例。F5 重载前端后单例重建，全部规则回到「未触发、从未通知」，启动评估看到的就是一次全新边沿，必然重报。应用完全退出重启同理——「6 小时冷却」的真实语义一直是「同一前端会话内」，不是墙钟时间。
- ADR-0022 曾否决「评估下沉 Rust」，理由是「主窗口 webview 崩溃时整个应用已不可用，不为它单独设防」。该论证只覆盖了崩溃场景——release 构建的 WebView2 允许 F5/Ctrl+R 重载（用户可以、也会按），webview 重载而应用存活正是它没有考虑的形态。
- 通知本体早已落库（`notifications` 表，30 天/200 条保留），但表里没有规则键，无法从通知历史反推冷却状态；错误快照的冻结语义（ADR-0023）也使「从最新快照重评估派生边沿态」存在派生洞（最新快照为 error 时无从派生）。
- 冷却时长写死在协调器构造参数（`6 * 3_600_000`），设置里只有总开关。

用户决策（2026-09-11 访谈）：冷却采用**墙钟语义**（跨 F5、窗口重载、应用重启持续有效）；维持**边沿触发语义**（持续越阈只报一次，恢复后再越阈才再报）；冷却为**全局单值设置**；状态与判重**持久化到 Rust 端**，避免前端单点导致重复推送。

## Decision

**评估留在主窗口前端（ADR-0022 维持）；去重的状态与权威判重下沉 Rust。**

1. **状态事实源**：新增 `alert_states` 表（`rule_key` 主键，含 `instance_id`、`triggered`、`last_notified_at`）。协调器的边沿/冷却状态以它为事实源：主窗口启动链路（`loadInitial`）水合恢复；评估中状态实际变化时批量回写（`save_alert_states`，INSERT OR REPLACE）。水合只播种协调器里尚不存在的键——本次会话已写过的键比库里的快照新。
2. **后端冷却守卫**：`add_notification` 增加 `ruleKey` 参数并升级为判重入口——后端按墙钟冷却（读设置库）检查该规则的 `last_notified_at`，冷却期内拒绝落库并返回空；前端以「落库成功」作为发送系统通知的前提（先问后发）。守卫返回错误（而非拒绝）时仍发系统通知——投递韧性优先于判重。无规则键的调用（未来非告警类通知）不判重。
3. **冷却可配**：`AppSettings.alertCooldownHours`（默认 6），设置页用量告警卡内配置；协调器逐次评估时读取、后端守卫读库，两边同源。0 表示关闭冷却（边沿仍受边沿语义约束）。
4. **告警态即时恢复**：水合同时用 `triggered` 重建 `active` 表——F5/重启后托盘与面板的告警态不再依赖下一轮成功刷新才回来；错误快照期间的冻结态（未知 ≠ 正常）原样恢复。
5. **级联清理**：`delete_instance` 连带删除该实例的 `alert_states` 行，与快照/通知同口径。

## Considered Options

- **派生水合**（`notifications` 加 `rule_key` 列 + 从最新 OK 快照重评估派生边沿态）：不引入新表，但错误快照冻结语义下派生有洞，且派生要么复制评估逻辑到 Rust、要么依赖前端取到「最新 OK 快照」；显式存状态比重构状态便宜且完全忠实。
- **全量评估下沉 Rust**：ADR-0022 的否决理由仍成立（后端要理解快照与阈值语义，改动面大）；本次的证据只要求「状态与判重」下沉，评估的输入输出结构不必搬家。
- **仅修 F5 不落盘**（状态放 Rust 进程内存）：重启后仍重报，与用户拍板的墙钟语义不符。

## Consequences

- F5、面板重载、应用重启后，冷却与边沿态原样恢复，同一状况不再重复推送；冷却按用户设置的真实时间计算。
- 存量库没有 `alert_states` 行：升级后首轮对当前活跃状况可能重报一次（一次性，接受）。
- 系统通知与通知中心两条通道由「各自为政」变为「落库成功才发通知」——数据库故障时仍尽力投递系统通知（判重降级），正常运行下两通道不再可能单边重复。
- 协调器新增可注入的水合与回写依赖，单元测试可以覆盖「重载后不重报」「冷却到期后再报」等持久化场景。
- 与 ADR-0022 的关系：修订其「告警状态只活在前端内存」的隐含前提，评估权唯一化与文案模板化结论不变。

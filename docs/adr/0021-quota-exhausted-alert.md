# 额度耗尽告警：任一配额窗口撞满即告警

Status: accepted

补上 ADR-0016 告警口径的一个盲区：阈值告警只盯主指标（重置周期最长的预算窗，GLM=周窗、OpenCode Go=月窗），防的是 5h 短周期窗「日常冲高」造成的告警噪音。但代价是：预算窗远低于阈值、而 5h 窗撞满（用户实际已无法使用该供应商，须等重置）时，任何配置下都不会产生告警——恰恰是最该知道的时刻静默。

## Context

告警系统的现状（2026-09-11 代码核对）：

- `evaluateRules` 按供应商产出规则，阈值规则只比较主指标：OpenCode Go 月窗 ≥ 阈值（规则 `monthly`）、GLM 周窗 ≥ 阈值（规则 `quota`）、余额类独立阈值（规则 `balance`）。
- 盲区场景：OpenCode Go 阈值 80%，月窗 40%、周窗 95%、5h 窗 100%——`monthly` 不触发，实例零告警。5h 窗从 99% 涨到 100% 的那一刻（配额真正耗尽、请求开始失败）完全不可见。
- 阈值告警的定位是「接近预警」：80% 时提醒省着用。它天然不适合承担「已耗尽」的表达——把阈值规则改盯最紧窗（任一窗 ≥ 阈值即告警）会让 5h 窗的日常冲高（重度用户每天发生）驱动告警，等于每天红一次图标、发一次通知，逼用户关掉告警。

## Decision

**新增与阈值无关的公共规则：任一配额窗口已用 ≥100% 即告警（规则键 `${instanceId}:exhausted`）。阈值规则原样不动。**

1. **撞满是终值条件，不存在误报面**：100% 意味着该窗在重置前已不可用，这是定义上值得知道的信息；「接近但未到」的模糊区间留给阈值规则。两者的分工：主指标阈值 = 预算预警（提前省着用），耗尽规则 = 失可用告警（立刻换个窗/等重置）。
2. **多窗同时撞满合并为一条告警**：通知正文逐一列名撞满的窗口（`「5 小时请求配额」「每周请求配额」已用尽（100%）`），规则键不分窗——实例级一条边沿，避免多窗先后撞满时的重复打扰。
3. **接入现有边沿/冷却机制**：`exhausted` 作为独立规则键进 `AlertCoordinator`，窗口重置（百分比回落）即解除告警态，6 小时冷却与其余规则一致，受总开关 `alertsEnabled` 门控。窗口label 模板占位符（如 `{hours}`）经 `applyParams` 还原后进通知文案。

## Considered Options

- **阈值规则改盯最紧窗（任一窗 ≥ 阈值）**：概念最简（只剩一个口径），但 5h 窗日常冲高会让重度用户天天收告警，与 ADR-0016 以来「阈值只盯预算窗」的防噪音设计直接冲突。
- **告警窗口可配置（每实例选择按哪扇窗告警）**：灵活但配置面扩大，需要重新设计阈值 UI，收益配不上成本（YAGNI，同 ADR-0020 对设置项的取舍）。
- **100% 改为可配置的「耗尽阈值」**：耗尽不是偏好而是客观状态，可配置只会引入「设 95% 算不算耗尽」的语义争议。

## Consequences

- 通知面多一种文案（「额度耗尽」）；`ruleKey` 规则清单扩展，新增窗口接入的供应商自动获得耗尽覆盖，无需各自实现。
- 与阈值告警可能同轮并存（周窗越线且 5h 撞满 → `quota` + `exhausted` 两条通知），语义各自独立成立。
- 主指标语义不变；CONTEXT.md 新增「额度耗尽」词条，「主指标」词条同步修正（托盘用量环已不以其为准——那是 ADR-0017 多层化之前的旧描述）。

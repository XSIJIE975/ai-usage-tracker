# 智谱 GLM 重置卡通道（用量重置额度）

Status: accepted

为智谱 GLM 供应商新增「重置卡」通道：读取官网「用量重置额度」（每张可立即恢复 5 小时/周窗口额度一次的赠送卡），与配额、余额并行拉取，同一枚 Coding Plan API Key 鉴权。

## Context

智谱近期向 Coding Plan 用户批量赠送「重置卡」（5 小时卡/周卡，独立有效期、过期作废，使用周卡会同步重置 5 小时窗口）。查看与使用此前只能上控制台网页。GitHub 无智谱重置卡的现成实现（codex-reset-card / CodexMeter 等均为 OpenAI Codex 生态），官方 glm-plan-usage 插件也未使用该接口。

用户于 2026-09-05 提供控制台抓包：`GET https://www.bigmodel.cn/api/biz/customer-package-reset/list?targetType=PERSONAL`，响应含 `fiveHourResets` / `weekResets`（每张卡 `recordId` / `expireTime`（服务端本地时间）/ `available`）、`lastFiveHourResetTime` / `lastWeekResetTime`；仅展示未使用或近 7 天已过期的记录。

## Decision

- 读取复用 Coding Plan Key（`bearer` 注入），与余额同属 biz 族私有接口（ADR-0013 同款模式）。
- 快照新增「可用重置卡」文本行，仅在可用张数 > 0 时渲染（无卡是常态，与 DeepSeek 充值/赠送行的按需展示一致）；明细（分组列表、每张卡有效期与状态）在统计抽屉 GLM 页签展示。**2026-09-29 修订（展示面：文本行 → 卡片底部按钮 + 弹窗）**：用一张卡是「有卡时才发生的一次小动作」，原路径却要穿过整个统计面板（查看统计 → 滚动过筛选条/概览/余额三块 → 重置管理 → 挑卡），抽屉为大块只读明细而存在，与这个动作错配。改为：可用张数 > 0 时供应商卡片底部出现「重置卡」按钮（张数做徽标、窗口拆分放 title，与「查看统计」并排，同 workbuddy「成长中心」那枚的排布），点击直接打开明细弹窗；**弹窗是明细的唯一宿主**，抽屉的「重置卡」摘要卡与其中入口一并撤除（功能换了宿主，不留两个并存的入口）。重置卡只占底部一枚按钮位、不在额度行区加行，本条原本「卡片别塞明细」的意图不变。张数读快照 `availableResetIds`（不新增请求；口径是**带 recordId 的可用卡**，没有 recordId 的卡本来就用不了，与弹窗组头按 `available` 计的「可用 N 次」在真实响应里同数），无卡与该源本轮失败都不出按钮——源失败仍由快照 message 点名报错，不会因为没按钮而静默；代价是可用数为 0 时看不到「已使用/近 7 天已过期」的记录（那批记录只在有卡时可见，本 ADR 认这个损失）。连带效果：抽屉不再每轮预取重置卡列表——省掉的是**抽屉打开时那一路重复请求**（快照自己的 RESET_URL 请求照旧每轮发，见 Consequences），改为每次打开弹窗按需重取——`recordId` 必须新鲜，否则点到的是用过或已过期的卡。
- 卡片状态推断：`available=true` → 可用；不可用且已过期 → 已过期；不可用但未过期 → 已使用。
- 不只做展示——「使用重置卡」一并接入：接口规约取自官网前端源码静态分析（2026-09-05，`claude-usage~glm-coding-ent-usage-stats` bundle）：`POST /api/biz/customer-package-reset/use`，JSON body `{ targetType: "PERSONAL", resetType: "FIVE_HOUR"|"WEEK", recordId, requestId }`，`requestId` 为客户端生成的幂等 UUID；成功判定 `code===200 && success===true`；`msg` 为「指定的重置次数不可用，请刷新后重试」时官网会自动刷新列表，本应用在 UI 提示刷新。使用属不可逆动作，UI 经二次确认弹窗；成功后同步刷新重置卡列表与实例快照。**2026-09-29 修订（刷新时机与失败回话）**：成功后不再原地重取列表——弹窗关闭，只刷新实例快照（配额窗口数值已变，走 Dashboard 既有的 `refreshInstance` 单刷链），列表新鲜度由「每次打开弹窗都重取」保证，比留一份常驻列表再补一路请求更省。失败同样要退出二次确认层：确认框自带遮罩，不退就把失败原因压在背后，用户只看到一个卡住的确认框（原抽屉同款缺陷）；黄条给「重试」重取列表，且取数失败与使用失败各占一条、不合并——合并会让「列表陈旧」吞掉一次不可逆动作的失败回话。
- 写通道已于 2026-09-05 用户实测（curl 真实过期卡）：HTTP 400 + `code=400` + `msg`「指定的重置次数不可用，请刷新后重试」——与官网源码的特殊错误串逐字吻合，鉴权、参数路由与业务校验全部正确。业务错误可能携带非 200 的 HTTP 状态，实现优先解析业务 `msg` 再看 HTTP 状态。尚无 `success=true` 样本（当时无可用卡），成功路径待用户拿到可用卡后首次使用验证。

## Consequences

- 快照每轮刷新多一次请求（三路并行，失败静默降级为快照消息）。
- `expireTime` 为服务端本地时间无时区标记，按本地时间解析展示（与 tool-usage 的 `x_time` 同约定）。
- 私有接口无兼容性承诺；纯订阅账户或未收到赠送的账户返回空列表，属正常态不报错。

# ADR-0039: WorkBuddy 活跃上报与日常判据落库

状态：已接受　日期：2026-10-08　关联：ADR-0029、ADR-0031、ADR-0036、ADR-0037

## 背景

用户报告连登好像要在 WorkBuddy 里真的对话才算活跃。本机 DB（`snapshots` / `workbuddy_checkins`）取证证实了这个观察：大号、小号签到天天成功（`notified_date=2026-10-08`），连登天数却长期停在 0~3 并在 10-03 归零、10-05 起卡片连登行整个消失（`parseStreakLine` 对 `days<=0` 返回 null），同期小号喵喵旅行行照常出——growth 域是通的。也就是说**签到天天在做，连登照样归零**。

参考项目 linguo2625469/workbuddy2api-panel 的 `upstream/report.go` 与 `scheduler/scheduler.go:742 runActivity` 给出了机制：点亮连登的是客户端每次发起对话时上报的 `chat_request_send` 行为事件（`POST /v2/report`，`conversationId` 由调用方自造、服务端不校验对应真实会话，事件体必带 `userId`，缺失则返回成功但静默不计分），签到接口只管发积分。本工具的 `reportChatActivity` 只在手动点成长任务时发过，没有任何每日上报，所以天数只在用户真的对话时才涨——与用户的观察一致。

由此暴露两个既有偏差：`CONTEXT.md` 把「连登」定义成「连续签到天数」是错的；日常例程的**动作判据**（今日已签、这趟已领过、今天管家跑过、trial 已处理、今天续过期）全在模块级内存 Map 里，而**通知判据**另存四张表，重启后前者失效、同一天重做一遍，同一件事两个地方各说各话。

## 决策

1. **术语修正**：「连登」改为连续**活跃**天数，新增「活跃上报」词条；签到与连登明确为两套互不相干的运营（一个发每日积分，一个记天数换档位奖励）。ADR-0037 的连登管家（补签/兑换/抽奖）不受影响，它处置的一直是这套天数。

2. **每日一条活跃上报挂「每天第一次刷新」链，紧跟签到、在连登回读之前，不设独立开关**（`runDailyActivityReport`）。顺序是判据的一部分：本轮读回的天数必须是「上报之后」的值，否则抽屉那行的「已上报但天数为 0」判定不成立。频率口径照参考项目「每号每天 1 次」，由 `activity_acted` 格保证跨重启成立。这是对 ADR-0036「伪造事件上报只在手动触发下纳入」的边界扩张：一次性任务仍全部手动，日常活跃改成自动——理由是这个功能的全部价值就在「不断」，手动形态等于把连续性寄托在用户每天记得点。程序没开的那天必断，补签卡是唯一事后补救（既有能力），不为此做独立排程器（ADR-0037 决策 9 不动）。

3. **日常判据全部落库，一张通用表**：`workbuddy_states(instance_id, kind, value, updated_at)`，主键 `(instance_id, kind)`，一对 `get_workbuddy_state` / `save_workbuddy_state` 命令，级联删除一句 `WHERE instance_id=?1`。一格一判据，`*_acted` / `*_tried`（动作做过没有）与 `*_notified`（通知发过没有）分格并存；`cookie_account` 格永久留存 Cookie 通道的 uid。旧四张表（`workbuddy_checkins` / `_travel_claims` / `_growth_notices` / `_trials`）打开时整块 DROP，**刻意不搬旧数据**：这些格子都是幂等动作与通知的节流标记，升级当天最坏多发一次幂等请求或多通知一条，之后自愈。内存 Map 与「会话投影」一并退役——投影会读到过期值（抽屉「最近一次领取」正是会变的那种），而两个地方各说各话正是这次要消灭的状态。

4. **拿不到 uid 就不发**：发了也不计分，唯一效果是多一条无归属的埋点，还把「没做」和「做了没效」弄成同一个样子。原因写进 `activity_status` 格，界面明说（ADR-0024）。

5. **状态行只在成长中心抽屉的连登区块，一行承载全部真相**：今日已上报 / 今日已上报但连登天数仍为 0 / 今日未上报（缺 uid）/ 今日未上报（上次失败原因）。卡片不加常驻行——连登行本身就是天数事实源，再加一行就是同一个状态两个控件；不做手动补跑按钮（自动链已覆盖，缺 uid 时补跑同样无效；管家的 `force` 先例是「用户要当场看结果」的场景）；不发系统通知（「当天上报当天计入」只有参考项目的间接证据，先攒自己的数据）。

6. **国际站放开 `streak`（读）与 `activity`（上报），写面照旧全关**：签到、旅行、档位兑换、抽奖、成长任务维持不发——参考项目对 global 账号的门控矩阵正是这样（只有活跃上报没被 global 挡，PR #91 专门放开）。成长中心抽屉入口仍按 `tasks` 门控，所以国际站这一轮的证据面是**卡片连登行会不会出现**：出现即这套运营在国际站存在，再谈要不要给它开兑换与抽屉。

7. **上报出站从任务层下沉到成长中心层**：事件形状、`/v2/report` 出站本体、按通道的域与头族分流、uid 占位符与替换，一处实现，任务动作与每日例程共用。这是 ADR-0037「新增成长接口只写一次」的延续，也避免同一事件两份字段表被上游加严时只改一处。

## Considered Options

- **只给活跃上报建新表，旧内存标记不动**：否。同一件事一半在内存一半在库，正是当前「重启后重做已做过的动作」的根因。
- **每件事一张表（再建 checkin_actions / butler_runs / activity_reports 等）**：否。这个项目每几个月就加一个日常动作，每次都写 DDL + 一对命令 + 级联 + 测试；`kind` 化之后加动作零 DDL。
- **保留旧四张表 + 新通用表并存**：否。两种持久化风格并存，以后没人知道该往哪写。
- **国际站维持不发**：用户否决，要求与参考项目对齐并拿到第一手证据。相应地读面必须一起开，否则成了只能做不能验证的动作。
- **上报失败发系统通知**：否，判据未自有实证之前会制造假警报。
- **把旧表数据搬进新表**：否，一次性迁移代码是功能债（这些判据本来就会自愈）。

## 真机验证清单

- [ ] 国区两号自 2026-10-08 起连登天数是否真的从 0 开始累加（这是本决策成立与否的唯一判据）
- [ ] 「当天上报、当天计入」——上报后同轮回读 `streak.days` 是否已含今天
- [ ] 国际站 `GET /activity/growth/streak` 是否出数（决定要不要给它开档位兑换与抽屉入口）
- [ ] Cookie 通道 `console/account` 失败时回落 `cookie_account` 格的真实行为
- [ ] 常驻代报会不会引起官方侧异常（观察项：天数正常累加、账号未被要求重新登录、消耗明细无多余条目）

## 后果

连登天数从「用户碰巧对话才涨」变成程序每天补齐；日常动作判据重启后不再失效，代价是一次跨 Rust/前端的数据层重构与旧表废弃。伪造客户端埋点从「用户主动点一下」变成常驻自动发送，风控后果由用户承担（面板风险提示沿用 ADR-0036）。

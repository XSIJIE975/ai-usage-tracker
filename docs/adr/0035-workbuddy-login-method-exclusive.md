# WorkBuddy 登录方式互斥:扫码与 Cookie 二选一

Status: accepted

## Context

ADR-0034 落地了扫码登录,凭据形态为**双通道并存 + 隐式优先级**(token 非空即走 token 通道,否则三格):表单里扫码区块与 Cookie 三格纵向堆叠同显,一行文案说明当前生效通道,已扫码时三格仍在(仅免必填);新增弹窗则完全没有扫码入口——扫码会话在 Rust 侧以 `instance_id` 为键,实例必须先落库。

用户真机使用一轮后的反馈:这个混合交互不好。扫码登录与 Cookie 手填是两件心智上完全不同的事(一个扫一下、一个 F12 抄三值),堆在一起既不知道该用哪个,也不理解「退出扫码后自动改用下方三格」的隐式回落。要求:**两种方式互相独立互相区分,新增和编辑时只能选择其中一种登录,不混杂**。

此外新增流程存在体验断层:想扫码的用户必须先填三格把实例建出来,再回编辑弹窗扫码——最方便的录入方式反而要多走一步最麻烦的录入。

## Decision

**六条,经 grilling 会话逐条确认(2026-09-26):**

1. **数据层互斥,不新增状态字段**:一个实例任一时刻只有一种登录方式的凭据。取数侧「accessToken 非空即 token 通道、否则校验三格」的判定(ADR-0034 D4)**原样保留**——互斥数据上隐式优先级退化为确定性的,无需引入 ADR-0034 否决过的 authChannel 持久字段,也不出现「选了 Cookie 但实际走 token」的错位。代价是 ADR-0034 担忧的「退路丢失」(扫码实例切回 Cookie 需重抄三格),权衡后接受:扫码成本近零、三格本就是最麻烦的录入,心智清晰更值。
2. **清槽时机跟随各通道既有写入模式**:扫码侧即时——扫码确认写 token 五槽的同时清三格(扫码通道本就是「写库即生效」);Cookie 侧走保存——保存时清 token 五槽并写三格(表单哲学「中途取消什么都没被改掉」)。每边遵循该通道的写入模式,互斥不变量在各自生效时刻成立。
3. **无实例扫码(改 Rust,新增弹窗内直接扫)**:`qr_start(site)` 以站点发起、以上游 state 作会话键(它已是二维码里的曝光值,无新增敏感面);`qr_poll(会话键)` 确认后 token 换到并**暂存 Rust 内存**(凭据全程不过前端——ADR-0034「前端不接触明文凭据」的架构约束不变),15 分钟 TTL;新增 `qr_claim(instance_id, 会话键)` 把暂存凭据写入该实例 vault 并顺手清三格。编辑态扫码确认后前端自动 claim(保留「写库即生效」);新增态扫码确认后显示「扫码成功:昵称」,**等用户点保存**才创建实例 + claim + 关弹窗(扫完不保存关弹窗=白扫,重扫成本近零)。
4. **表单交互**:凭据区顶部(站点选择之后)分段控件「登录方式」,两选项「扫码登录 / Cookie 手填」,下方**只渲染所选方式的区块**——选扫码不见三格,选 Cookie 不见扫码区块与续期开关。编辑态初值按实例生效通道(token 非空即扫码);新增与未配置实例默认扫码(主推路径,新用户免 F12)。切换瞬间显示一行内联后果提示(如「保存后将改用 Cookie 登录,扫码凭据将被清除」),不弹窗不阻断。「退出扫码登录」清 token 五槽转「未配置」,该按钮只在扫码方式下可见。
5. **未就绪保存校验拦截,按净效果判定**:保存时比「当前选择」与「实例生效方式」,不一致且新方式凭据未就绪(扫码未确认/三格未填全)→ 校验拦下报错;切过去又切回=净效果未变,凭据不动正常保存。与其它供应商「新增必须带凭据」同一哲学,防止误操作把生效实例静默拆成待配置。
6. **存量双份数据不主动收敛**:此功能随 ADR-0034 同期未发布,无迁移负担;打开弹窗按 token 非空显示扫码方式,不动就保存则凭据不动,历史双份在下次切换保存或扫码确认时自然清掉。不做「打开表单顺手清库」的静默收敛。

## Considered Options

- **显式通道字段 authChannel(ADR-0034 已否决,理由仍立)**:互斥后两套凭据不会同时非空,字段没有存在必要;「选了 Cookie 但 token 还在」等组合状态在新模型里直接不可能发生。
- **仅 UI 分离(分段控件只控显示,底层照旧并存)**:会出现「界面选了 Cookie、取数仍走 token」的错位,违背「互相独立」的诉求。否。
- **「保存并扫码」(前端改造:保存后弹窗不关转编辑态自动扫码)**:复用现有命令、改动最小,但留下「先建待配置实例再扫」的中间态,与无实例扫码的体验不成比例地割裂。用户选择彻底方案。
- **新增态扫码即完成(确认回调里自动建实例)**:体验更顺但「没点保存实例就建好了」剥夺用户对生效时机的控制,且备注/阈值必须在扫码前定稿。否。
- **扫码产物返回前端由表单提交写入**:违背「前端不接触明文凭据」(CONTEXT.md 凭据库词条、ADR-0034 实现约束)。否,以 Rust 暂存 + claim 替代。
- **存量双份主动收敛(首次保存/打开弹窗时清非生效方)**:「打开不动保存后我的三格没了」是静默改库,违背最小惊讶;未发布无迁移负担,不值得一惊一乍。否。
- **未就绪保存放行(允许存出未配置实例)**:编辑态下会把生效实例静默拆成待配置(token 清、三格空),典型误操作事故;与其它供应商新增校验不一致。否。

## Consequences

- **正面**:表单一次只见一种登录方式,心智模型从「两个区块+优先级说明」变为「一个二选一」;新增流程与编辑流程对称,扫码从「先建实例再扫」变为弹窗内直接扫;互斥不变量让取数通道判定无需解释。
- **代价**:扫码实例切回 Cookie 需重抄三格(ADR-0034 当初否决互斥的理由,本次权衡后接受);新增态扫完不保存关弹窗白扫一次;扫码三命令签名全变(前端是唯一调用方,无兼容负担)。
- **维护面**:Rust 侧多一个暂存凭据的内存结构(state 键、15 分钟 TTL)与 claim 命令;`resolveWorkbuddyChannel` 及取数链零改动。
- 文档:本 ADR 修订 ADR-0034 的 Decision 1(Cookie 保留为并存退路)与 Decision 4(隐式优先级+表单明示当前生效)——判定逻辑本身保留,但其语义从「并存时的优先级仲裁」变为「互斥数据的确定性读出」;CONTEXT.md 新增「登录方式」词条并修订「WorkBuddy 登录凭据 / token 通道 / Cookie 通道 / 扫码登录」。
- **待真机验证**:新增态全流程(弹窗内扫码→保存→卡片就绪)、切换保存的清槽时序、扫码成功自动 claim 的编辑态路径。

# 错误必须可见

Status: accepted

2026-09-11 全库审查发现的系统性模式：**错误被吞掉之后状态悄悄漂移**——同一个病灶在 Rust 与前端各有三四处变体。本 ADR 把修复统一为一条仓库级原则：失败必须可见或可重试。

## Context

审查确认的实例（同一模式的不同变体）：

| 位置 | 病灶 | 后果 |
| --- | --- | --- |
| `tray_scheme.rs` `apply()` | 呈现指纹在 setter 执行**前**记账（锁内 `replace`），setter 的 Err 全部 `let _ =` | setter 失败后指纹已声称写入成功，内容不变则永不重写——告警红点长时间缺席 |
| `db.rs` `get_settings` | 读失败 `.ok()` 静默回全套默认值 | 用户此刻点任何保存，真实设置被默认值整体覆盖（快捷键、自启、语言全重置） |
| `lib.rs` setup | `if let Ok(settings)` 静默跳过；`quick.hide()?` 让优化性操作失败阻断启动 | 读设置失败连带跳过快捷键/自启重放且无日志；隐藏工具窗口失败会让应用拒绝启动 |
| `commands.rs` `apply_quick_shortcut` | 先注销旧组合、再注册新组合 | 注册失败时旧组合已失效且不恢复，静默丢快捷键 |
| `lib.rs` setup | 托盘菜单/tooltip 初始语言硬编码 `"zh"` | en 用户每次启动先看到中文托盘，直到 webview 加载后才纠正 |
| `Dashboard.tsx` | `void removeInstance(...)` fire-and-forget | 后端删除失败无任何提示，且 unhandled rejection |
| `useAppStore.ts` `invokeWithTimeout` | 超时后输掉分支的 promise 无人接 | unhandledrejection 噪音 |
| `commands.rs` 两个网络命令 | reqwest Client 无超时、每次调用重建 | 供应商挂起 → 自动刷新静默停摆；每轮轮询重新 TLS 握手 |

共性：每一处单独看都「只是吞了个小错误」，合起来是同一个设计缺口——**代码把「没观察到失败」当成了「成功」**。

## Decision

**仓库级原则：失败必须可见或可重试。所有错误处理路径按下面三条规则之一落位：**

1. **状态只在写入成功后提交**：呈现指纹、缓存、内存记账一律在底层写入成功之后才更新；写入失败按字段回滚到上一份已验证状态，让下次重试成为可能。
2. **多步变更保序**：凡「删旧建新」类操作（快捷键换绑等），先建立新状态成功、再拆除旧状态；半途失败时用户手里始终握着上一个可用状态。
3. **可见性分层**：用户能行动的失败上抛到 UI（错误横幅、设置页提示）；用户无法行动的至少 `eprintln!` 留痕（带上下文，不吞栈）；纯优化性操作（隐藏窗口、预取）降级为日志后继续，不阻断主流程。

同批落地：reqwest Client 构建一次入 `AppState` 复用（连接池/keep-alive），统一 10s 连接 / 30s 总超时——超时走 ADR-0023 的错误快照链路，可见而不是挂死。

## Consequences

- 「先记账后提交」「先删后建」「静默 `.ok()`」在 code review 里有据可依地被拒；新代码的错误处理有了默认答案。
- `get_settings` 签名变为 `Result`，调用方（前端设置页）需处理读失败态——比静默默认值更诚实，代价是一条新的错误文案。
- 托盘指纹回滚引入「setter 失败 → 保留旧指纹」路径：Explorer 重启等竞态下内容会在下一次 `apply()` 自动补写，托盘自愈。
- 超时是显式取舍：慢网络下 30s 可能误判偶发慢响应为失败，但它走的是可见的错误快照而非无限挂起；参数集中在一处，调优不涉及结构。
